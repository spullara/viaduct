# Viaduct Development Instructions for AI Agents

> **Purpose**: This guide provides comprehensive instructions for AI agents to understand and build Viaduct applications based on the framework patterns, examples, and architecture found in this repository.

## Overview

Viaduct is a GraphQL-based system providing a unified interface for accessing and interacting with data sources. It's built on three core principles:
- **Central Schema**: Single, integrated schema connecting all domains
- **Hosted Business Logic**: Teams host business logic directly in Viaduct
- **Re-entrancy**: Logic composes by issuing GraphQL fragments and queries

## Project Structure Patterns

### 1. Multi-Module Architecture

Viaduct applications typically use a multi-module Gradle structure:

```
project-root/
├── build.gradle.kts              # Root build configuration
├── settings.gradle.kts           # Module declarations
├── gradle/
│   └── libs.versions.toml        # Version catalog for dependencies
├── modules/                      # Domain-specific modules
│   ├── {domain1}/               # e.g., filmography, universe
│   │   ├── build.gradle.kts     # Module build config
│   │   └── src/main/kotlin/     # Module source code
│   └── {domain2}/
└── src/main/kotlin/             # Main application (Spring Boot)
    └── com/example/{app}/
```

### 2. Module Internal Structure

Each domain module follows this consistent pattern:

```
module/src/main/kotlin/com/example/app/modules/{module}/
├── {entity}/                    # One folder per entity type
│   ├── models/                  # Domain models and repositories
│   │   ├── {Entity}.kt         # Data class
│   │   └── {Entity}Repository.kt
│   ├── queries/                 # Top-level query resolvers
│   │   └── {Entity}Queries.kt
│   ├── mutations/               # Mutation resolvers (optional)
│   │   └── {Entity}Mutations.kt
│   └── resolvers/              # Field resolvers
│       ├── {Entity}NodeResolver.kt
│       ├── {Entity}FieldResolver.kt
│       └── {Entity}BatchResolver.kt
└── viaduct/schema/             # GraphQL schema definitions
    ├── {Entity}.graphqls
    ├── {Entity}Queries.graphqls
    └── {Entity}Mutations.graphqls
```

## GraphQL Schema Conventions

### 1. Schema File Organization

- **One schema file per entity**: `Character.graphqls`, `Film.graphqls`, etc.
- **Location**: `src/main/viaduct/schema/` within each module
- **Auto-discovery**: Viaduct scans for `*.graphqls` files using package prefix

### 2. Essential Directives

```graphql
# Scope-based access control
type Character @scope(to: ["default"]) {
  name: String
  # Only available with "extras" scope
  secretInfo: String @scope(to: ["extras"])
}

# Custom field resolution
type Character {
  filmCount: Int @resolver        # Requires custom resolver
  homeworld: Planet @resolver     # Cross-entity reference
}

# Strong typing for ID references
type Character {
  homeworldId: ID @idOf(type: "Planet")
}

# Union input types
input CharacterSearchInput @oneOf {
  name: String
  id: ID
  birthYear: String
}

# Explicit resolver binding
type Character {
  summary: String @resolver @backingData(class: "CharacterSummaryResolver")
}
```

### 3. Node Interface Pattern

All entities should implement the Node interface for global ID support:

```graphql
type Character implements Node {
  id: ID!
  name: String!
  # other fields...
}
```

## Resolver Implementation Patterns

### 1. Resolver Class Hierarchy

```kotlin
// Base resolver (generated by Viaduct)
abstract class CharacterResolvers {
    abstract class Name : FieldResolver<Character, String>()
    abstract class FilmCount : FieldResolver<Character, Int>()
}

// Implementation
@Resolver
class CharacterNameResolver : CharacterResolvers.Name() {
    override suspend fun resolve(context: Context): FieldValue<String> {
        return FieldValue.ofValue(context.objectValue.name)
    }
}
```

### 2. Batch Resolution (Critical for Performance)

```kotlin
@Resolver(objectValueFragment = "fragment _ on Character { id }")
class CharacterFilmCountBatchResolver : CharacterResolvers.FilmCount() {
    override suspend fun batchResolve(contexts: List<Context>): List<FieldValue<Int>> {
        // Extract all IDs from batch
        val characterIds = contexts.map { 
            it.objectValue.getId().internalID 
        }.toSet()
        
        // Single batch query
        val filmCounts = FilmRepository.getFilmCountsByCharacterIds(characterIds)
        
        // Map results back in order
        return contexts.map { ctx ->
            val id = ctx.objectValue.getId().internalID
            FieldValue.ofValue(filmCounts[id] ?: 0)
        }
    }
}
```

### 3. Node Resolvers

```kotlin
@Resolver
class CharacterNodeResolver : CharacterQueries.Node() {
    override suspend fun resolve(context: Context): FieldValue<Character?> {
        val globalId = context.argumentValue.asGlobalId()
        val localId = globalId.internalID.toInt()
        val character = CharacterRepository.findById(localId)
        return FieldValue.ofValue(character?.let { CharacterBuilder(context.executionContext).build(it) })
    }
}
```

### 4. Query Resolvers

```kotlin
@Resolver
class AllCharactersResolver : CharacterQueries.AllCharacters() {
    override suspend fun resolve(context: Context): FieldValue<List<Character>> {
        val limit = context.argumentValue.limit ?: 10
        val characters = CharacterRepository.findAll().take(limit)
        val builder = CharacterBuilder(context.executionContext)
        return FieldValue.ofValue(characters.map { builder.build(it) })
    }
}
```

## Data Layer Patterns

### 1. Repository Pattern

```kotlin
object CharacterRepository {
    private val characters = mutableMapOf<Int, Character>()
    private val idGenerator = AtomicInteger(1)
    
    fun findAll(): List<Character> = characters.values.toList()
    
    fun findById(id: Int): Character? = characters[id]
    
    fun findByIds(ids: Collection<Int>): Map<Int, Character> =
        ids.mapNotNull { id -> characters[id]?.let { id to it } }.toMap()
    
    fun add(character: Character): Character {
        val id = idGenerator.getAndIncrement()
        val withId = character.copy(id = id)
        characters[id] = withId
        return withId
    }
}
```

## Configuration Patterns

### 1. Viaduct Configuration

```kotlin
@Configuration
@Import(ViaductResolverRegistrar::class)
class ViaductConfiguration(private val codeInjector: SpringTenantCodeInjector) {
    
    companion object {
        val DEFAULT_SCHEMA_ID = SchemaScopeId("default")
        val EXTRAS_SCHEMA_ID = SchemaScopeId("extras")
    }
    
    @Bean
    fun viaduct(): Viaduct {
        return BasicViaductFactory.create(
            schemaRegistrationInfo = SchemaRegistrationInfo(
                scopes = listOf(
                    DEFAULT_SCHEMA_ID.toSchemaScopeInfo(),
                    EXTRAS_SCHEMA_ID.toSchemaScopeInfo()
                ),
                packagePrefix = "com.example.starwars",
                resourcesIncluded = ".*\\.graphqls"
            ),
            tenantRegistrationInfo = TenantRegistrationInfo(
                tenantPackagePrefix = "com.example.starwars",
                tenantCodeInjector = codeInjector
            )
        )
    }
}
```

### 3. Spring Boot Integration

```kotlin
@RestController
class ViaductRestController(private val viaduct: Viaduct) {
    
    @PostMapping("/graphql")
    fun graphql(
        @RequestBody request: GraphQLRequest,
        @RequestHeader headers: Map<String, String>
    ): GraphQLResponse {
        val scopes = parseScopes(headers["X-Viaduct-Scopes"])
        val schemaId = if (scopes.contains("extras")) EXTRAS_SCHEMA_ID else DEFAULT_SCHEMA_ID
        
        val input = ExecutionInput.Builder()
            .query(request.query)
            .variables(request.variables ?: emptyMap())
            .context(mapOf("scopes" to scopes))
            .build()
            
        val result = viaduct.execute(schemaId, input)
        return GraphQLResponse(result.getData(), result.getErrors())
    }
}
```

## Development Workflow

### 1. Start with Schema Design

1. **Create GraphQL schema files** in `src/main/viaduct/schema/`
2. **Define types, queries, mutations** with appropriate directives
3. **Use `@resolver` for computed fields**
4. **Apply `@scope` for access control**

### 2. Implement Data Layer

1. **Create domain models** (Kotlin data classes)
2. **Implement repositories** with batch query methods
3. **Add necessary indexes or query optimization**

### 3. Build GraphQL Objects

1. **Create builder classes** for converting domain models to GraphQL types
2. **Handle global ID generation** using `ctx.globalIDFor()`
3. **Manage cross-entity references**

### 4. Implement Resolvers

1. **Start with node resolvers** for global ID lookups
2. **Add query resolvers** for top-level fields
3. **Implement field resolvers** with batch optimization
4. **Add mutation resolvers** if needed

## Performance Best Practices

### 1. Always Use Batch Resolution

- **Implement `batchResolve()`** instead of `resolve()` for field resolvers
- **Extract all required data** in a single database call
- **Return results in the same order** as input contexts

### 2. Repository Batch Methods

```kotlin
// Good: Single query for multiple IDs
fun findCharactersByIds(ids: Set<Int>): Map<Int, Character>

// Bad: N queries
fun findCharacterById(id: Int): Character?
```

### 3. Fragment-Based Data Fetching

```kotlin
@Resolver(objectValueFragment = "fragment _ on Character { id homeworld { id } }")
class CharacterHomeworldResolver : CharacterResolvers.Homeworld() {
    // Only fetches necessary data based on fragment
}
```

## Common Patterns and Conventions

### 1. Naming Conventions

- **Packages**: `com.example.{app}.modules.{module}.{entity}.{layer}`
- **Resolvers**: `{Entity}{Field}Resolver`, `All{Entities}Resolver`
- **Mutations**: `{Action}{Entity}Mutation` (e.g., `CreateCharacterMutation`)
- **Repositories**: `{Entity}Repository`

### 2. Error Handling

```kotlin
override suspend fun resolve(context: Context): FieldValue<String> {
    return try {
        val result = performOperation()
        FieldValue.ofValue(result)
    } catch (e: BusinessException) {
        FieldValue.ofError(GraphQLError.newError()
            .message(e.message)
            .build())
    }
}
```

### 3. Scope-Based Development

- **Use default scope** for public data
- **Use extras scope** for privileged data
- **Check scopes in resolvers** if needed:

```kotlin
override suspend fun resolve(context: Context): FieldValue<String?> {
    val scopes = context.executionContext.getContext<Map<String, Set<String>>>()["scopes"]
    return if (scopes?.contains("extras") == true) {
        FieldValue.ofValue(sensitiveData)
    } else {
        FieldValue.ofValue(null)
    }
}
```

    return object : GraphQLWebMvcConfigurer {
        override fun configureWebMvc(builder: WebMvcConfigurer.Builder): WebMvcConfigurer {
            return builder
                .introspection(true)
                .build()
        }

### 2. Add Request Logging

```kotlin
@Component
class GraphQLRequestLoggingInterceptor : DataFetcherExceptionResolverAdapter() {
    private val logger = LoggerFactory.getLogger(javaClass)
    
    override fun resolveToSingleError(ex: Throwable, env: DataFetchingEnvironment): GraphQLError {
        logger.error("GraphQL execution error at path ${env.executionStepInfo.path}", ex)
        return super.resolveToSingleError(ex, env)
    }
}
```

## Summary for Agents

When building Viaduct applications:

1. **Start with schema-first design** using GraphQL schema files
2. **Organize code by domain modules** with consistent internal structure
3. **Always implement batch resolvers** to avoid N+1 query problems
4. **Use repository pattern** with batch query methods
5. **Follow naming conventions** for predictable code organization
6. **Implement proper error handling** and validation
7. **Use scope-based access control** for sensitive data
8. **Write comprehensive tests** at both unit and integration levels
9. **Configure proper observability** for production deployment

The key to success with Viaduct is understanding its resolver execution model, batch optimization patterns, and modular architecture principles.
